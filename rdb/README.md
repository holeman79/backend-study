# RDB 조회 성능 공부

실제 테이블과 데이터를 넣고 **눈으로 확인한 것만** 적는다. 실험마다 전/후 쿼리·`EXPLAIN ANALYZE` 결과·소요 시간을 그대로 남긴다.

## 환경

| 항목 | 값 |
|---|---|
| DB | MySQL 8.0 (docker, 로컬) |
| 데이터 | [hotdeal](https://github.com/holeman79/hotdeal) 프로젝트의 상품 200만 행을 기반으로, 부족한 주문 데이터는 생성 스크립트로 채운다 (예정) |
| 작업 스키마 | 원본을 건드리지 않도록 같은 컨테이너에 사본 스키마를 만들어 쓴다 (예정) |
| 측정 | `EXPLAIN` / `EXPLAIN ANALYZE`, 실행 시간 |

## 공부 항목

아래 9개 중 **필요하다고 느끼는 것만** 골라서 한다. 순서표가 아니라 메뉴다.

| # | 항목 | 내용 |
|---|---|---|
| 1 | 쿼리 자체 개선 | `SELECT *` 제거 · 불필요한 JOIN 제거 · 서브쿼리 → JOIN / `EXISTS` · OR·함수 연산·형변환 때문에 인덱스를 못 타는 조건 개선 |
| 2 | 조회 데이터 양 줄이기 | `LIMIT` 페이지네이션 · 커서(no-offset) 페이지네이션 · 필요한 컬럼만 · 앱이 안 쓰는 데이터 안 가져오기 |
| 3 | JOIN 최적화 | JOIN 대상 먼저 줄이기 · 불필요한 다중 JOIN 제거 · N+1 해결 · 경우에 따라 반정규화 |
| 4 | 테이블 구조 변경 | 과한 정규화 → 일부 반정규화 · 조회 전용 컬럼 · 계산 결과 미리 저장 |
| 5 | Partitioning | 날짜별 파티션으로 실제 스캔 범위를 줄인다 |
| 6 | 캐시 | Client → Redis → (miss) DB. 반복 조회는 DB 쿼리를 안 하는 게 가장 빠르다 |
| 7 | Materialized View / 집계 테이블 | `SELECT user_id, SUM(amount) FROM orders GROUP BY user_id` 를 매번 하지 않고 미리 만들어 둔다 |
| 8 | 읽기 Replica | 단일 쿼리가 빨라지진 않지만 조회 트래픽을 분산한다 |
| 9 | Execution Plan 분석 | `EXPLAIN` / `EXPLAIN ANALYZE` — 실제 튜닝은 여기서 시작한다. 1~8 전부의 전/후를 이것으로 잰다 |

## 기록 규칙

- 실험 하나 = `experiments/NN-<주제>/` 폴더 하나. 안에 `README.md`(무엇을 왜 · 전/후 · 결론), `before.sql`, `after.sql`, 실행 계획 원문.
- 숫자는 실측만 적는다. 추정치는 "추정"이라고 표시한다.
- 결론이 난 실험만 블로그로 옮긴다.
